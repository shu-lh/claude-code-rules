# Core Engineering Discipline [MUST]

## 1. Surgical Changes [MUST]

只改目标代码，不动相邻代码、注释、格式。

- 不"顺手"修改变量名、格式化、重构
- 匹配现有代码风格，即使不认同
- 清理自己引入的 dead code，不动原有的

另见 interaction.md §6 任务范围控制——§1 约束单次编辑的精度（怎么改），§6 约束改动范围（改什么）。

### Project Instantiation
在新项目中，需在项目规则中指定：
- 存在格式化工具时（clang-format 等）：禁止手动格式化
- 存在历史遗留代码：标注遗留区路径，不做清理
- 存在 generated code：列出生成代码路径，禁止修改

## 2. Simplicity First [MUST]

不做未要求的事。

- 不加未要求的功能
- 不为单次使用创建抽象
- 不加未要求的"灵活性"或"可配置性"
- 不为不可能的场景加错误处理
- 测试标准："资深工程师会觉得过度设计吗？"

### Project Instantiation
在项目规则中明确项目的复杂性标准：
- 什么是"过度设计"的边界（根据项目规模调整）

## 3. Think Before Code [MUST]

- 遇到歧义时先问，不要猜
- 有更简单方案时主动提出
- 困惑时停下来请求澄清
- 不确定时说明假设

## 4. Goal-Driven Execution [MUST]

- 将任务转化为可验证的目标
- 多步骤任务：说明计划 + 每步的验证标准
- 优先用可运行的测试验证

## 5. Rule Conflict Resolution [MUST]

规则优先级：项目规则 > 全局规则 > 系统默认。

当全局规则和项目规则冲突时：
- 项目规则优先（具体 > 通用）
- 在项目规则中显式标注覆盖了哪条全局规则："[覆盖: rules/xxx.md §N]"

## 6. Architecture Compliance [MUST]

项目中若存在软件设计架构规则或类似说明（如 `.claude/rules/architecture.md`），在进行代码修改时必须遵循：

- 修改前检查相关架构约束，确保方案不违反
- 如果修改不得不突破现有架构约束，必须征求用户同意，并给出：
  - 架构修改方案
  - 影响范围（哪些模块/层受影响）
  - 替代方案（如果有）
- 架构约束包括但不限于：分层依赖方向、生命周期、数据流、接口契约

## 6a. 跨文件架构预检 [MUST]

涉及跨目录/跨层文件操作时，**编码前**先做强制架构审查。

### 6a.1 触发条件

以下变更必须执行预检（任一即触发）：
- 新增/移动/删除的文件跨越 2 个以上顶层目录
- 修改的文件分布在 2 个以上架构层
- 引入新的抽象接口或修改现有接口签名
- 新建顶级目录

### 6a.2 审查四步

1. **枚举** — 列出所有新建/移动/修改的文件，标注归属层
2. **查依赖方向** — 逐个文件检查 include 是否违反 `<上层>→<下层>` 单向约束
3. **查目录语义** — 目录名是否准确反映功能分类（如 `Estimator` 不应放非估算功能）
4. **查已有模式** — 同类功能是否已有约定放置位置，不建重复目录

### 6a.3 输出格式

审查结果必须在编码前以表格输出：

```
[ARCH-PRE-CHECK] 跨层变更预检：
  <层>/<目录>/<文件> — <职责> ✓
  <层>/<目录>/<文件> — <职责> ✗ 原因: ...
允许实施 / 驳回修正
```

### 6a.4 违规处理

- 审查未通过 → 修正后重新审查，不跳过
- 审查通过但实施中偏离 → 暂停并重新审查
- 本规则与 §6 互补：§6 处理有意识突破架构的审批，本规则防止无意识违反架构

## 7. Session Startup Check [MUST]

每次会话启动时，先确认运行环境：
- 操作系统类型（Linux/macOS/Windows），据此选择正确的命令语法
- AI 对话环境（Claude Code CLI / VSCode 插件 / IDE 集成），了解可用功能和限制
- 当前工作目录和项目上下文
- 避免调用当前环境不支持的命令或工具

## 8. Error Recovery [MUST]

工具调用失败时，按以下策略处理：

### 8.1 首次失败

验证输入参数是否正确（路径、文件名、字符串内容是否与当前文件一致），修正后重试 1 次。

### 8.2 再次失败

切换方式重试：
- Read 失败 → 检查路径是否存在（Glob）
- Edit 失败 → 重新读取文件确认内容未变，扩大匹配上下文
- Bash 失败 → 检查命令语法和依赖
- 网络类（WebFetch/WebSearch）失败 → 不重试，直接告知用户

### 8.3 放弃条件

以下情况停止重试并告知用户：
- 同一操作连续失败 2 次（已排除输入错误）
- 工具返回明确错误表明操作不可执行（权限、文件不存在、语法错误）
- 超过上下文预算（此时优先保护已完成的成果）

告知格式：
```
[ERROR] <操作> 失败：<原因>。建议：<替代方案或手动操作步骤>
```

### 8.4 例外

- 网络类工具（WebFetch/WebSearch）首次失败即放弃——非本地可控
- 编译/构建类命令（cmake --build）失败后，先获取完整错误输出再决定是否重试，不盲目重试
