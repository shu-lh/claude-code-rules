# Rule Change Notification [MUST]

## 0. Request Classification [MUST]

用户要求"添加/修改 X"时，先判断 X 是 Rule 还是 Skill，再路由到对应流程：

| 判断依据 | 分类 | 路由 |
|---------|------|------|
| 行为约束、自动检查条件、无需用户触发 | Rule | → §6 放置逻辑 / §7 扩展优先 |
| 用户调用的命令、含交互步骤、一次性操作 | Skill | → `skill-management.md` §5 生命周期 |

具体分类标准见 `skill-management.md` §1.2 决策矩阵。

## 1. Core Principle [MUST]

Claude 可以**建议**规则变更，但**绝不**在用户未确认的情况下修改规则文件。

## 2. Trigger Scenarios

| 场景 | Claude 的行为 |
|------|-------------|
| 时效检查发现参数变化 | 列出变化清单 → 等待确认 → 执行更新 |
| 项目实践发现规则不适用 | 解释原因 + 建议新规则 → 等待确认 |
| Claude 犯错后自省 | 说明根因 + 建议增改规则 → 等待确认 |
| 发现两条规则冲突 | 说明冲突点 + 建议方案 → 等待确认 |
| 项目架构重大变更 | 列出受影响文档/规则 → 等待确认后更新 |

## 3. Notification Format [MUST]

```
[RULE-CHANGE] 建议变更：<规则文件名>
原因：<为什么需要改>
当前：<当前规则内容摘要>
建议：<新规则内容>
影响：<改后有什么不同>
是否执行？(yes/no/edit)
```

## 4. User Response Handling [MUST]

- `yes` → 执行变更并记录到 `state/rule-changelog.md`
- `no` → 不做任何修改
- `edit: <修改意见>` → 按用户意见调整后重新确认

## 5. Cascading Update Check [MUST]

规则变更确认并执行后，Claude 必须检查是否需要连带更新：

### 5.1 检查范围

| 被改规则 | 需连带检查 |
|---------|-----------|
| 任何全局规则 | `~/.claude/CLAUDE.md` 索引是否需要同步 |
| 任何全局规则 | `~/.claude/USER_GUIDE.md` 是否需要更新 |
| 涉及 Project Instantiation 段的规则 | 所有使用该模板的项目规则是否需要同步 |
| 规则文件被重命名/拆分/合并 | 所有引用该规则的文件（CLAUDE.md 索引、其他规则中的交叉引用） |
| 工具选择或效率规则变更 | `tool-selection.md`、`efficiency.md` 是否一致 |
| 严重级别变更（MUST↔SHOULD） | 索引文件和排序是否需要调整 |

### 5.2 跨层同步

全局规则变更可能影响项目规则：

1. 判断此变更是否属于"模板实例化"类型（即全局规则定义了需要在项目中填写的参数）
2. 若是 → 列出受影响的已知项目
3. 输出建议格式：
   ```
   [CASCADE] 此变更可能影响以下文件：
     - ~/.claude/CLAUDE.md — 索引需更新
     - ~/.claude/USER_GUIDE.md — 用户文档需更新
     - 项目/.claude/rules/xxx.md — 派生自被修改的规则
   是否一并更新？
   ```

### 5.3 无关性声明

如果确认无需连带更新，简短说明原因（如"该规则为直接继承型，不涉及模板参数，无需同步项目规则"）。

## 6. Rule Placement Logic [MUST]

用户要求添加新规则时，Claude 自动判断放置位置：

1. 此规则是否属于已有规则文件的范畴？
   - 是 → 在现有文件中增加章节
   - 否 → 判断是否需要新建规则文件

2. 此规则的适用范围？
   - 所有项目通用 → `~/.claude/rules/` 中对应领域文件
   - 特定技术栈 → `~/.claude/rules/<技术栈>/` 下
   - 仅当前项目 → `项目/.claude/rules/` 下

3. 判断依据：
   - 概念相关性：规则描述的概念是否已在某文件中出现
   - 触发频率：高频独立关注面 → 独立文件；低频附属规则 → 并入已有文件
   - 粒度控制：单文件超过 80 行 → 考虑拆分

## 7. Extend Before Create [MUST]

收到规则变更需求时，按以下流程决定文件归属：

1. **搜索现有规则** — 在所有已有规则文件中搜索"此规则描述的概念是否已被覆盖？"
2. **优先扩展** — 若能归入已有文件（增加章节或改写段落），绝不新建文件
3. **新建条件** — 仅当以下条件**全部**满足时才新建：
   - 概念在现有规则文件中完全不存在
   - 与任何现有文件的相关性无法通过扩展章节建立
   - 预期内容 ≥ 15 行有效规则（非格式/注释）
4. **复核** — 新建前自我复核："此内容若塞入最相关的现有文件是否真的不合理？"

此规则扩展自 §6 的放置逻辑：§6 解决"放哪"，§7 解决"是否必须新建"。

## 8. Rule Ordering [MUST]

规则增加或删除后，Claude 检查并维护结构清晰：

1. **按重要程度排序** — 规则项按重要性排序：核心约束在前（会话启动、环境检查），特定领域约束在后；[MUST] 排在 [SHOULD] 之前

2. **按主次关系排序** — 主规则在前，补充/例外在后；同一严重级别中按基础性/依赖关系排序

3. **CLAUDE.md 入口文件中**：
   - 规则引用列表按重要性排序
   - 基础规则（core/interaction/efficiency）在前，特定领域规则（embedded/git）在后

4. **触发条件**：
   - 新增/删除规则时
   - 修改规则内容时（重排受影响的相关项）
   - 用户要求 `整理规则排序` 时
